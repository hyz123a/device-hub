# Device Hub TDD 开发指南

本文不规定具体业务测试清单，而是定义 `device-hub` 的测试架构、开发原则和协作方式。目标是让后续功能都能在同一套 TDD 节奏下演进，而不是为某一批接口写一次性测试。

## 1. 设计目标

`device-hub` 是一个本地优先的控制面，核心特征不是页面或某个接口，而是这几个系统属性：

- 对外行为通过 HTTP 和事件流暴露。
- 内部状态由配置、注册表、任务管理器、事件总线共同驱动。
- 很多能力是异步的，且带有生命周期变化。
- 面向 AI 和人工两类调用方，协议稳定性比实现细节更重要。

因此，这个项目的 TDD 目标不是“把函数测满”，而是优先固化以下契约：

- API 合同稳定。
- 状态迁移可验证。
- 错误语义一致。
- 事件可观察、可过滤、可追溯。
- 重构不改变外部行为。

## 2. 测试分层

推荐采用三层测试结构，由内向外分别承担不同责任。

### 单元测试

用于验证小范围、低依赖的规则：

- 纯函数。
- 配置解析与转换。
- 状态过滤规则。
- 小型存储对象的读写与排序。

这一层追求的是：

- 反馈快。
- 定位准。
- 覆盖边界条件。

### 服务层测试

用于验证领域状态和异步流程：

- 任务创建与取消。
- 状态迁移。
- 事件发布。
- 组件之间的协作关系。

这一层的重点不是 HTTP，而是“系统内部是否按预期推进”。

### API 集成测试

用于验证系统对外承诺：

- 路由是否接线正确。
- JSON 序列化是否稳定。
- 状态码和错误体是否符合约定。
- 从入口到内部状态再到输出的整体行为是否成立。

凡是文档、前端、AI 调用方会依赖的行为，都应该优先由这一层固定下来。

## 3. 测试目录原则

推荐使用一个集成测试入口，再按主题拆分模块：

```text
server/
  tests/
    api/
      main.rs
      helpers.rs
      root.rs
      devices.rs
      actions.rs
      jobs.rs
      events.rs
```

目录设计原则：

- `main.rs` 只负责声明模块，不放测试细节。
- `helpers.rs` 统一承载测试启动、默认配置、公共断言、轮询工具。
- 其余文件按外部边界或系统能力拆分，而不是按源码模块机械镜像。
- 测试文件名表达“系统能力”，源码文件名表达“实现结构”，两者不必一一对应。

## 4. 测试基建原则

`helpers.rs` 是整个 TDD 体系的底座。它应只解决测试搭建问题，不承载业务判断。

建议统一抽象：

- `spawn_app()`：启动真实服务实例，绑定随机端口。
- `TestApp`：封装地址、客户端和常用请求入口。
- `test_config()`：生成最小但有代表性的测试配置。
- 如需替换设备执行能力，优先通过 `server` 暴露的测试 seam 注入端口级依赖，而不是在测试里直接引用具体 adapter crate。
- 通用等待工具：用于异步状态轮询。
- 通用断言工具：用于错误响应、JSON 结构、状态码检查。

基建设计原则：

- 优先复用生产初始化路径。
- 避免测试自己重新拼装另一套应用。
- 避免每个测试单独复制请求构造和轮询逻辑。
- 避免在 helper 中掺入具体业务语义。
- 避免让集成测试直接依赖 `device-hub-adapter-*` 具体实现；如果必须替换外部行为，应先在 `server` 边界增加稳定注入接口。

## 5. TDD 工作流

统一采用 Red -> Green -> Refactor：

1. 先写一个失败测试，只描述一个外部行为。
2. 运行最小范围测试，确认失败原因正确。
3. 写最小实现让它通过。
4. 消除重复，收敛到 helper 或内部抽象。
5. 再补边界场景和错误场景。

这里的关键约束：

- 一次只推进一个行为。
- 不在“让测试变绿”的同时偷偷引入多个新特性。
- 先固定可观察行为，再优化内部结构。

## 6. 测试命名原则

测试名称统一表达“行为 + 结果”，不要表达实现步骤。

推荐风格：

- `root_returns_service_metadata`
- `list_devices_returns_sorted_devices`
- `start_action_rejects_unsupported_action`
- `cancel_job_marks_running_job_as_cancelled`

避免风格：

- `test_api_1`
- `job_manager_works`
- `calls_validate_action_before_insert`

命名原则：

- 面向行为，不面向内部函数。
- 失败时能直接读出哪条契约被破坏。
- 同一模块里的测试名称保持语义和语法一致。

## 7. 架构驱动的优先级

新功能进入 TDD 时，优先级不由“容易写”决定，而由架构风险决定。

优先固定：

- 外部协议。
- 状态机。
- 并发和取消语义。
- 错误模型。
- 事件流过滤与回放。

其次再补：

- 内部辅助函数。
- 低风险样板代码。
- 明显由类型系统已经保障的简单映射。

判断优先级时，问自己三个问题：

- 这个行为是否会被其他模块、前端或 AI 调用依赖？
- 这个行为是否容易在重构中被无意破坏？
- 这个行为出错时，是否会导致系统难以诊断或恢复？

## 8. 面向异步系统的测试原则

`device-hub` 不是纯同步 CRUD 服务，因此测试必须接受“最终一致的瞬时过程”。

建议：

- 对异步状态使用轮询等待，不写脆弱的固定时序断言。
- 对事件流测试，区分“最终出现”与“立即出现”。
- 对取消语义，重点验证最终状态和不可逆结果。
- 对时间相关逻辑，尽量把依赖收敛在 helper 或抽象层。

不建议：

- 依赖精确毫秒级顺序。
- 让测试和实现共享同一段判断逻辑。
- 用大量 `sleep` 替代有条件的等待。

## 9. 重构原则

当测试逐渐增多时，允许为测试友好性重构生产代码，但重构应遵守边界。

允许的重构：

- 抽出 `lib.rs` 以复用应用入口。
- 收敛初始化逻辑。
- 为状态轮询或依赖注入增加稳定接口。
- 降低模块耦合度，让状态和副作用更容易验证。
- 为测试增加基于端口的注入 seam，使测试替身停留在 `server` 抽象层，而不是穿透到具体 adapter crate。

不应为了测试而做的事：

- 暴露只给测试使用、但会污染正式 API 的业务入口。
- 复制一套专用测试初始化路径。
- 在生产代码里加入仅服务于断言的临时分支。

## 10. 持续维护原则

这份指南的作用是约束未来开发方式，而不是冻结今天的测试文件列表。

后续新增能力时，应保持：

- 新能力先补失败测试，再写实现。
- 新测试先放到现有能力模块；只有主题明显不同才新建文件。
- helper 只增长共性能力，不吸收偶发逻辑。
- 每次重构后至少运行对应模块测试和完整服务测试。

一句话总结：`device-hub` 的 TDD 核心不是“多写测试”，而是用分层测试把协议、状态机和可观察性当成系统架构的一部分长期维护。
